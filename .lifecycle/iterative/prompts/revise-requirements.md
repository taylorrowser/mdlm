# Revise the accepted requirement graph

Apply the approved change to the exact authoring frontier supplied by the CLI. Revise statements whose meaning changes; preserve unchanged parents and children. The CLI refreshes affected groups and queues their individual-child and collective decomposition review. Use optional decomposition outputs as described in typed-requirements for membership changes or explanatory prose made misleading by the approved change. Never reauthor descendants just to refresh a relationship.

Preserve the CLI prospective source impact before editing code. After publishing the new RQS, refresh native expectations with `mdlm expectations --json`. Complete fresh requirements review when offered, then follow rebind guidance. Rebind requires fresh source attribution and source/evidence dispositions, canonical Docker verification, independent implementation review and stakeholder acceptance. Submit authored fields through mdlm proposal submit.

To expand an accepted component into the agreed whole product, obtain a change targeting its stakeholder scope, revise affected obligations and add focused stakeholder roots or child obligations as needed. Keep one obligation per requirement when scope grows, and revise affected architecture/depth rationale. Preserve exact scoring or other obligations whose meaning is unchanged. New requirements may use optional `informed-by` EXP/OBS links just as initial requirements do.

For an allowed implementation change, state that the obligations remain unchanged in the approved change. Publish a new RQS selection with the same exact REQs and DCPs where appropriate; the new selection binds the change without inventing requirement revisions. When no requirement or decomposition changes, submit only the supplied RQS candidate, preserving its predecessor and guidance links, and omit unused REQ/DCP placeholders. Do not copy `contains` or `decomposition` links from the prior RQS; the CLI generates those selections. Native expectations may proceed directly to rebind when the existing selector can reuse a valid earlier requirements PASS in the same RQS lineage. The selected exact REQ and DCP revisions must match that earlier reviewed graph and the exact accepted baseline named by the current approved CHG, with no applicable FAIL veto. Changed requirements or decomposition require fresh requirements review. Do not declare reuse or copy a review; follow the eligible native action. Fresh source attribution, canonical verification, independent implementation review and stakeholder acceptance still follow. Record that process cost.

For interface-dependent behavior, add optional uses-interface links to exact ICD revisions. State each obligation in the REQ and cite the ICD clauses that define its representation; do not copy clause content, paths or tables into the REQ. Descriptive and provisional choices stay in the ICD. Adopting a changed ICD in accepted scope requires the normal approved requirement change and fresh applicable evidence.

New stakeholder roots require exact statements in the approved CHG `new_roots` declaration. Match each statement to one new stakeholder root and author its new downward branches and groups in the same batch. The CLI supplies `changes-under` provenance. Reuse each admitted root identity during later corrections; the declaration cannot authorize another root with the same statement. Existing requirements still need their ordinary frontier permission for edits or retirement.
