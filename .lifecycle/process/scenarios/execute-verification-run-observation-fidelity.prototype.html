Throwaway logic prototype

Can a formal result prove it observed the activities reviewers approved?

What is the smallest data and constraint model that stops a formal RUN and RES from claiming success when their observations do not correspond to the reviewed VER activities, while keeping the kernel process-neutral and adding no lifecycle artifacts?

Hard limit. Package constraints can prove that submitted observation values match reviewed machine-readable expectations. They cannot prove that a process really produced those values. That stronger claim needs an executable oracle or a trusted execution boundary.

Two package-only models

Prototype verdict

The smallest useful change is one machine-readable expectation map in the existing VER payload and one observation map with the same keys in the existing RUN payload. The package completion rule permits an existing RES pass only when both key sets are exact and every captured value equals the reviewed value. Missing expected data cannot support pass. No new Lifecycle Datum type or revision is needed.

Merely copying activity names into RUN.activities_expected and RUN.activities_invoked does not work. Pi227 shows why: labels can agree while the actual cases and values drift.
