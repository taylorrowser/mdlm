# Inputs for MDLM Process Overview v0.8 Provisional

**Status:** Historical source material consumed by the accepted `mdlm-process-overview-v0.8.md`.
This document remains the decision and completeness checklist; it is not itself
the process overview.

This document consolidates the decisions, terminology, prototype evidence,
behavioral discoveries, unresolved risks, and writing constraints that should
shape the next provisional overview. It exists so the overview can be written
from an explicit record rather than reconstructed from conversation or inferred
from prototype code.

## Post-draft acceptance decisions

Before accepting v0.8, the model was sharpened in three additional ways:

1. MDLM core is process-structure-neutral. The full V-model and type catalog are
   the first bundled Example Process Package, not the one hard-coded MDLM process.
2. The CLI is divided into generic core commands, explicitly selected Kernel
   Capability commands, and safe declarative Package Command Aliases. Commands
   such as `req dwp`, `req vsp`, and `req change` are example-package conveniences.
3. Expressions run only inside the evaluator. The CLI provides package
   capabilities, expression compilation and diagnostics, and direct relation,
   selector, policy, state, obligation, phase, and scenario inspection. Packages
   cannot install arbitrary code or expression host functions.

These decisions are recorded as D-011 and D-012 in the prototype decision log and
are integrated into the overview's four-part structure.

## 2. Evidence labels for the overview

The overview should distinguish four confidence levels wherever useful:

- **Validated by vertical slice** — exercised through a public interface with a
  behavior test or runnable example.
- **Provisional and implemented** — represented in process data or code but not
  yet exercised deeply enough to treat as validated.
- **Specified, not implemented** — intended target behavior inherited from v0.7
  or newly clarified here.
- **Deferred** — deliberately outside the current profile.

The word “implemented” must not imply the durable repository kernel or complete
`req` CLI exists.

## 3. Architectural decisions to carry forward

### 3.1 Retain the four-layer architecture

Keep the separation among:

1. hard-coded kernel;
2. declarative process package;
3. CLI semantic surface;
4. implementation profiles.

The vertical slice strengthened rather than weakened this model. Candidate member
review completeness, backlinks, process drift, staleness, and gate behavior were
derived without adding process-specific evaluator branches.

### 3.2 Make the kernel/process seam typed and deliberately small

The kernel exposes typed primitives, collections, and relations. It must not
expose conclusions such as `candidate.members_missing_review` or
`review.is_current` as bespoke facts.

Initial primitive categories are:

- identity and revision values;
- type-owned payload access;
- storage editability and frozen state;
- parse, schema, identity, reference, and hash integrity;
- process provenance;
- stable data, revision, and baseline collections;
- outgoing and incoming links;
- lineage revisions;
- baseline members, evidence, composition, and memberships;
- conservative dependency-change records;
- scenario inputs and outputs.

Adding a primitive changes the kernel interface version. Adding a selector over
existing primitives changes only the process package.

### 3.3 Separate the kernel-owned datum envelope from process-owned payload

Every lifecycle revision has one non-overridable kernel envelope containing:

- stable identity;
- revision identity;
- lifecycle type;
- a payload container;
- stored outbound links;
- creation provenance;
- Markdown body projection.

Lifecycle type definitions validate only payload fields and source-owned links.
Process data may not weaken identity, revision, immutability, or provenance.

Kernel-computed storage and integrity values are evaluator projections, not new
durable Markdown fields. Mechanically populated durable claims, such as the BSL
snapshot section, are declared as kernel-managed payload paths.

### 3.4 Use deterministic single-parent payload templates

The initial hierarchy is:

```text
titled-datum
  └── rationale-bearing
        └── requirement
              ├── STK
              └── SYS
```

Templates are additive, not arbitrary macros or classes. A child may add required
fields and tighten supported constraints. It may not remove required fields,
change field types, or widen constraints.

The initial composable JSON Schema subset should be deliberately limited rather
than attempting general schema-subsumption proofs. The exact allowed narrowing
operations remain to be specified.

### 3.5 Keep outgoing link contracts with their source type

A resolved type should contain everything needed to author and validate its
outgoing links: relationship ID, target kinds and types, stable-versus-revision
identity, cardinality, freeze resolution, and inverse display label.

Backlinks remain computed. Repeated relationship IDs on different source types
are acceptable; each source contract is authoritative. Package validation may
later enforce semantic compatibility among repeated IDs without restoring a
separate normative link registry.

### 3.6 Retain reusable parameterized selectors

Selectors are named relational queries with typed parameters. They are the
primary process-level vocabulary for higher-order facts such as:

- valid review contexts for a subject;
- passing reviews for a subject;
- candidate members missing review;
- current candidate baselines;
- applicable disposition decisions;
- recorded and applicable gate sign-offs;
- newer accepted or editable revisions.

Selector reference graphs must be acyclic and type-correct.

### 3.7 Retain machine-readable policies

Policies are deterministic prioritized decision tables with typed parameters,
a typed result, a default result, and expression-based rules.

The bootstrap demonstrated review applicability and waiver applicability as
machine policy. Rubric prose remains Markdown, while applicability and outcomes
remain structured data.

### 3.8 Keep state dimensions independent

Maturity, disposition, validity, and relationship/provenance overlays remain
separate dimensions. Process drift is an informational overlay, not staleness.
Accepted revisions may be stale without losing historical acceptance.

State dependencies must be derived from expression references and form an
acyclic graph.

### 3.9 Keep obligations as the unit of process work

An obligation definition selects exact subjects and declares satisfaction,
status, resolver, bindings, and waiver policy. One evaluated obligation for one
subject and process reference is an Obligation Instance.

Artifacts do not receive a global work status. Work status belongs to obligation
instances.

### 3.10 Separate eventual resolver from current dispatchability

A loose end may know its eventual Resolver Scenario while being unsafe to
dispatch. The result model should distinguish:

- obligation status;
- whether a resolver is dispatchable now;
- blocking obligation instances or missing bindings;
- eventual resolver;
- currently actionable resolver, when different;
- expected outputs;
- waiver eligibility.

A blocked loose end must never be dispatched merely because it names a resolver.

### 3.11 Keep scenarios declarative

Scenarios retain typed inputs and outputs, link requirements, prohibited inputs,
prompt reference, policy reference, completion condition, batching behavior, and
resolved obligation classes.

Scenario execution is an adapter over the scenario contract. Prompts select and
order skills. Execution provenance records what was actually loaded and used.

### 3.12 Keep phases obligation-driven

Phases declare entry, applicable scenarios, obligations, outputs, candidate
selection, and gate completion. They do not encode an imperative script.

The next evaluator result should include phase entry and gate evaluation rather
than only filtering obligations by phase.

## 4. MDLM Expression Language decision

### 4.1 Canonical term

Use **MDLM Expression Language** for the process logic language. Do not call it
“universal language,” because that can be confused with the project’s ubiquitous
domain language in `CONTEXT.md`.

### 4.2 Authoring rule

Whenever a process field represents a value, condition, predicate, binding, or
quantifier, author it as an MDLM Expression Language source string. Use YAML for
structural declarations.

This replaces author-authored YAML ASTs such as:

```yaml
when:
  all:
    - exists:
        selector: gate-signoff-decisions-for@1
        arguments:
          candidate: {var: candidate}
    - none:
        selector: applicable-gate-signoffs-for@1
        arguments:
          candidate: {var: candidate}
```

with:

```yaml
when: >-
  exists("gate-signoff-decisions-for@1", {candidate: candidate})
  && none("applicable-gate-signoffs-for@1", {candidate: candidate})
```

### 4.3 Fields that should use expressions

At minimum:

- selector `where` clauses;
- policy rule `when` clauses;
- state rule `when` clauses;
- obligation `satisfied_when` and status `when` clauses;
- scenario input conditions and completion conditions;
- phase entry and gate completion;
- selector arguments;
- resolver input bindings;
- subject, state, policy, count, and selection values.

Selector and relation declarations, parameters, schemas, output contracts, policy
results, and catalogs remain structural YAML.

### 4.4 Initial language capabilities

The v1 language should support:

- string, number, boolean, null, array, and object literals;
- bound variables and typed field access;
- `==`, `!=`, `>`, `>=`, `<`, and `<=`;
- membership, containment, and matching;
- `&&`, `||`, and `!`;
- parentheses;
- safe built-in functions;
- fact-to-fact comparison;
- selector quantification and selection.

Initial host functions should include equivalents of:

```text
state(subject, dimension)
policy(policyRef, arguments)
select(selectorRef, arguments)
exists(selectorRef, arguments)
none(selectorRef, arguments)
count(selectorRef, arguments)
one(selectorRef, arguments)
```

No assignments, mutation, arbitrary functions, unbounded loops, filesystem or
network access, dynamic code loading, or general-purpose evaluation are allowed.

### 4.5 Compilation model

At package load:

```text
source string
  → parse with source locations
  → typed internal AST
  → resolve variables, fields, selectors, policies, states, and argument types
  → reject cycles and impossible bindings
  → cache compiled expression
  → evaluate repeatedly against snapshots
```

The existing YAML AST is useful as an internal representation but should not
remain the authoring interface.

Expression errors must include definition path, line, column, offending source,
and useful reference suggestions.

### 4.6 Language versioning

The manifest should declare an exact language version, for example:

```yaml
language:
  expressions: mdlm-expression@1
```

Baselines and creation provenance capture the process manifest that fixes the
language version. A language-version change does not itself stale historical
lifecycle evidence.

### 4.7 Implementation choice still open

The semantics above are decided. The parser implementation remains technical and
reversible. The prototype may use a constrained CEL-style grammar or a small
purpose-built parser, but it must compile to the same safe typed AST and may not
use JavaScript `eval`.

## 5. Vertical-slice findings to incorporate

### 5.1 Declarative behavior changes worked

The strongest architectural evidence is that the gate defect was fixed through
process data:

1. add a selector for recorded gate-signoff decisions;
2. distinguish recorded decisions from reviewed applicable decisions;
3. add a higher-priority blocked status rule.

No evaluator special case was required.

### 5.2 Recorded gate sign-off is not immediately applicable

A gate-signoff DEC may exist while its required review remains outstanding. In
that condition:

- the candidate gate is blocked;
- the gate scenario must not be dispatched again;
- individual review-context and review obligations for the DEC drive the next
  work;
- the DEC becomes applicable only after required review passes.

The overview should make this loop explicit so an orchestrator cannot create
duplicate gate decisions.

### 5.3 Ready work should lead human and agent output

Definition-file order produced confusing output in the first slice. The current
provisional ordering is:

1. ready;
2. awaiting-review;
3. failed;
4. stale;
5. blocked.

Stable subject and obligation ordering break ties. This is presentation behavior,
not lifecycle truth, and may evolve after usability testing.

### 5.4 Runtime projection should remain separate from durable truth

The evaluator consumes durable datum envelopes plus kernel-computed storage,
integrity, and dependency-change projections. This allowed tests to vary
staleness and process drift without storing computed status in Markdown.

### 5.5 The three public seams provided useful depth

The current prototype interfaces are:

```text
loadProcessPackage(path)
resolveType(package, typeId)
evaluateLifecycle(package, snapshot)
```

They were sufficient to test package loading, schema composition, backlink and
baseline traversal, policy and state evaluation, obligation routing, and
explanations. Internal parsers and evaluators should remain behind these seams.

The CLI may expose several commands, but they should delegate to a small number of
deep kernel/process interfaces rather than reproduce logic in each command.

### 5.6 In-memory scanning is acceptable only for the prototype

The evaluator currently scans small snapshots to implement relations. This was a
useful choice while semantics changed and should not be elevated to target
architecture. Indexing should follow measured repository workloads.

## 6. Required improvements revealed by the slice

### 6.1 Loose-end result depth

The target loose-end result should contain:

- exact obligation instance identity;
- exact subject;
- current status;
- satisfaction evidence or failing condition;
- blockers as exact obligation instances or unresolved bindings;
- dispatchability;
- eventual and actionable resolver scenarios;
- prompt reference;
- expected output types and links;
- waiver policy and applicability;
- selector, policy, and process provenance sufficient to explain the result.

The current prototype returns only status, reason, and eventual resolver.

### 6.2 Complete package validation

The target validator must cover more than meta-schema parsing:

- manifest/catalog agreement;
- template cycles and legal narrowing;
- source-owned link compatibility;
- selector and policy references;
- expression syntax and types;
- variable and payload paths;
- selector argument kinds and cardinality;
- state and selector dependency cycles;
- resolver input bindings;
- scenario link requirements;
- obligation resolver coverage;
- policy priority conflicts;
- primitive interface compatibility.

### 6.3 Typed dependency-change records

`dependency-changes` is still the largest risk of hiding process semantics inside
the kernel. The overview should define it as conservative structural comparison,
not as a kernel judgment that an artifact is stale.

The relation should return typed records for changes such as:

- exact content;
- outgoing links;
- stable-link resolution;
- baseline membership or composition;
- evidence target;
- execution target;
- environment profile;
- allocation or interface once those types exist;
- review context.

Process expressions decide which records imply staleness for each claim.

### 6.4 Phase and gate evaluation

The next slice should return phase entry, selected candidates, gate completion,
and exact blocking reasons. The current evaluator only applies phase-specific
obligations.

### 6.5 Internal evaluator decomposition

Keep the three public interfaces, but separate private implementations for:

- package loading and validation;
- template/type resolution;
- graph projection;
- expression compilation and evaluation;
- query execution;
- policy and state evaluation;
- obligation and phase evaluation;
- explanation construction.

These are internal seams and should not become caller responsibilities.

## 7. Current scope and evidence

The implemented bootstrap covers:

- seven lifecycle types: PSP, STK, SYS, REV, BSL, QST, and DEC;
- three payload templates;
- source-owned links;
- two machine policies;
- four computed-state dimensions;
- twenty-four relational selectors;
- five obligations;
- eight scenarios;
- partial Phase 0 and Phase 2 definitions;
- a runnable PSP → STK → SYS snapshot;
- eleven public-interface behavior tests.

Observed behaviors include:

- template flattening for STK;
- package meta-schema validation;
- unknown selector and template rejection;
- template-cycle rejection;
- review-context readiness;
- passing-review backlinks;
- candidate member review completeness;
- conservative staleness;
- process drift as an overlay;
- reviewed gate-signoff applicability;
- actionable loose-end ordering.

This evidence does not yet validate durable file mutation, hashing, atomic writes,
concurrency, process migration, scenario execution, full gates, verification, or
production performance.

## 8. Deferred v0.7 capabilities that remain part of the target

The provisional overview must preserve, while marking unimplemented:

- DWP planning, completion, coverage, and simplification;
- ASP and ICSP definition;
- VSP, ENV, VER, VAI, RUN, and RES semantics;
- qualification, pilot, and formal verification distinctions;
- verification independence;
- implementation from DES;
- PRB and CHG flows;
- full baseline promotion and evidence reuse;
- phases 1 and 3–6;
- brownfield deferral;
- complete CLI command classes.

The evaluator refinement is not a reduction in lifecycle scope; it is a stronger
foundation for expressing that scope.

## 9. Open technical questions that do not require user answers now

1. Exact permitted JSON Schema narrowing operations.
2. Static path typing for polymorphic selector variables.
3. Typed dependency-change record schemas and comparison fixtures.
4. Compatibility rules for repeated source-owned link IDs.
5. Historical storage and explanation of obligation instances that fall out of a
   selector after revision.
6. Review-context batching policy and expected volume.
7. Machine baseline policy for role/kind agreement, member types, composition, and
   promotion.
8. Complete invalid-fixture organization.
9. CEL-compatible library versus purpose-built expression parser.
10. Index design after realistic performance measurement.

These should be implemented with reversible defaults and judged through behavior.

## 10. Product questions to test with users

These are more important than the technical choices above:

- Does the loose-end queue identify the work the user expects?
- Does each explanation make the cause and next action obvious?
- Are blocked and dispatchable work clearly distinguished?
- Is the review burden acceptable?
- Are shared review contexts understandable and economical?
- Does gate-signoff review provide confidence or merely ceremony?
- Do localized changes preserve the evidence users expect?
- Is the expression language readable enough for process authors?
- Can an agent safely author and modify process data without hidden kernel rules?

## 11. Writing constraints for v0.8 provisional

The next overview should:

1. use terms from `CONTEXT.md` consistently;
2. integrate the typed evaluator model into the main architecture rather than
   leaving it only in a companion appendix;
3. show textual expressions, not YAML AST examples;
4. identify the process package as normative for machine behavior;
5. distinguish target behavior from implemented profile behavior;
6. include the gate-signoff review loop and dispatchability distinction;
7. specify that process changes alone do not stale lifecycle evidence;
8. preserve v0.7 verification independence and prototype evidence boundaries;
9. avoid claiming full package validation or kernel implementation exists;
10. retain complexity discipline: new primitives require kernel justification,
    while new selectors and rules should remain process data.

complete expression grammar or generated type reference.
