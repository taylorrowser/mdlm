# Optional requirement levels for multi-component products

The iterative package (`mdlm-iterative@2.5.0`) adds two optional REQ payload fields, `level` (`system`, `high-level` or `low-level`) and `component`, for products whose architecture note names two or more separately running or separately replaceable components joined by an internal interface agreement, or whose stakeholder says a component may be replaced. Stakeholder requirements keep `kind: stakeholder` and carry neither field. System requirements state product-boundary or cross-component behavior and name no component. High-level requirements state one component's behavior against its interface clauses and owned state and stay implementation-neutral. Low-level requirements record design or realization decisions inside one component, such as runtime and launcher, persistence, concurrency control or a required algorithm. They are the only level that may name a language, and the only level a rewrite of that component replaces. Single-component products omit both fields and nothing changes for them.

This supersedes the part of ADR-0005, and of its 2026-09-09 requirement-graph successor, that ruled out distinct requirement levels. ADR-0005 dropped levels because the V-model route made them mandatory, verified each level separately and ran them as phases for one-component products; the requirements were renamed more than decomposed. None of that returns. Levels are optional metadata on ordinary `kind: software` REQs. A high-level requirement is decomposed into low-level ones only where a real decision exists, otherwise it stays a leaf and owns its code. Verification targets system and high-level requirements through interface clauses and entry points so activities survive a rewrite. Set-level review, shared verification activities and the existing change route still apply.

Three accepted fable products (2026-09-28) improvised level markers in titles and EARS subjects and put language choices into product-wide requirements and normative interface clauses. A one-component language rewrite therefore touched stakeholder, software and interface records. With levels and entry-point interfaces, such a rewrite targets that component's low-level requirements and any stakeholder constraint naming its language.

The kernel is unchanged. It still distinguishes only stakeholder and software requirements and attributes source to software leaves. The type schema checks the field combinations. The existing requirements review judges level-parent fit and implementation neutrality. Mechanical parent-order enforcement or a component impact filter waits for evidence that review misses them. Existing repositories keep their installed package, because the package is fresh-only.
