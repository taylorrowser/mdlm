River: from prototype choices to requirements

What is the smallest way to turn learning from a scorekeeping CLI into selected, justified requirements, while leaving the rest open to change?

This page simulates two ways to draft the same requirement records. All decisions and evidence here are demonstration data. Nothing updates MDLM or records your acceptance. The current packages do not support migration from exploration to requirements. Formal source coverage for a mixed provisional/formal artifact is not modeled here; the current tiny package covers its entire selected source inventory. This is a model to discuss, not an implemented lifecycle.

What to watch: does starting from a choice leave unnecessary solution detail in the draft? Can a new requirement be justified without a prior choice? Can one area become stable while the interface keeps changing?
The current MDLM kernel preserves typed identities and exact revisions. Changing a design record's type in place would change that contract. Both approaches here keep prototype choices and create separate requirements with optional provenance. No automatic promotion, requirement count target, review threshold or production authority rule is proposed by this page.
