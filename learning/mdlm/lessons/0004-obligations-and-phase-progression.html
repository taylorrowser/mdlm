Lesson 4 · 15 to 20 minutes

Obligations and Phase progression

An Obligation asks whether one requirement is satisfied. Phase progression asks whether MDLM may evaluate the next Phase.

Goal. Explain why progression does not wait for a general "all Obligations satisfied" check, then trace one bound Scenario input across two YAML definitions.

Four checks with different jobs

Obligation satisfaction
Whether one requirement has its declared evidence for one Subject.
Progression readiness
Whether the Phase's declared evidence condition is true.
Progression authorization
Whether exact evidence records the required human or policy authority.
Gate completion
Whether each selected gate candidate passes the Phase's declared gate check.

A Phase progression is complete only when its readiness, authorization, and required gate checks pass. There is no additional kernel rule requiring every Obligation Instance to be satisfied first.

Answer 1: progression does not wait

During one evaluation, MDLM computes applicable Obligation Instances and evaluates the progression conditions. Progression does not depend on a prior check that the Loose End list is empty.

Current package and Lifecycle Data
↓ one evaluation derives
Obligation results
Satisfaction, status, blockers, resolver, and dispatchability
+
Progression result
Readiness, authorization, gate completion, and next Phase

The implementation computes Obligations earlier in the function because the gate report can refer to them. That code order is not a rule saying all Obligations must pass before progression is checked.

If progression is complete, activeLifecycleEvaluation evaluates the declared next Phase. It does this even if the previous evaluation contained an unsatisfied Obligation Instance.

A correction about Loose Ends

A Loose End is any unsatisfied Obligation Instance that is not waived. It can be ready, blocked, awaiting review, failed, or stale. It does not need to be dispatchable or have currently usable inputs to remain a Loose End.

Therefore, an empty Loose End list means no unsatisfied, non-waived instances remain in that Phase evaluation. It still does not replace the progression expression.

Answer 2: when this becomes a package defect

The kernel lets the Process Package define its own evidence semantics. It does not assume that an empty Loose End list is the correct progression rule.

If a package describes an Obligation as mandatory before leaving the Phase, but progression can complete while that Obligation remains unsatisfied and unwaived, the package contradicts itself. That is a Process Package design defect.

The repair belongs in the package. Its progression expression, authorization condition, gate condition, or Obligation applicability must express the intended rule. Adding an unconditional kernel check would erase the package's ownership of process semantics.

Current Phase 0. Its progression expression names exact evidence: a candidate baseline, completed reviews, a passing simplification review, no unresolved correction authority, an intent approval, and no blocking questions. Its authorization and gate sections add exact signoff requirements.

Answer 3: one bound input

A Scenario input contract declares what a Scenario accepts. An input binding is the exact value selected for that input in one invocation.

The live compile-psp@3 Scenario declares this input:

inputs:
  - name: product_intent_authority
    types: [DEC]
    cardinality: one
    identity: revision

This contract requires exactly one specific Revision of type DEC. The Scenario does not choose that Revision.

The live product-specification-required@2 Obligation supplies the binding:

resolve_with:
  scenario: compile-psp@3
  inputs:
    product_intent_authority: >-
      first("applicable-initial-product-intent-decisions@1", {})

The expression calls a Selector, which is a named package query. first takes the first exact result. The selected DEC Revision becomes the value bound to product_intent_authority.

  1. The Scenario declares an input name and contract.
  2. The Obligation maps that name to an expression.
  3. MDLM evaluates the expression against current Lifecycle Data.
  4. MDLM checks cardinality, type, identity, and any input condition.
  5. If the check passes, the Assignment contains the exact bound Revision.
  6. If a required value is absent or invalid, the work is not dispatchable.

This is why the agent cannot replace the bound Decision with another convenient record. The Assignment fixes the input identity before the agent starts.
