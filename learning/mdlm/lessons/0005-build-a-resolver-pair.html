Lesson 5 · 15 to 20 minutes

Build a Resolver pair

Read an Obligation and its Scenario as two sides of one package-designed contract.

Goal. Explain every major field in one live Obligation and Scenario pair, including a Scenario with multiple inputs.

Terms for this lesson

Resolver pair
An Obligation and the Scenario it names in resolve_with.
Input contract
A Scenario declaration specifying an input's name, accepted types, number of values, identity kind, and conditions.
Input binding
An Obligation expression that selects the exact value for one Scenario input.
Invocation
One execution of a Scenario with one complete set of bound inputs.
Package validation
Kernel checks that reject malformed or internally inconsistent Process Package definitions before work runs.

First correction: there are no input Obligations

A Scenario can declare multiple Lifecycle Data inputs. It does not receive multiple Obligations as inputs.

One Resolver Assignment is authorized by one Obligation Instance. That Obligation's resolve_with.inputs section must bind every input declared by the Scenario.

The Scenario does not search for matching Obligations. The Obligation names an exact Scenario version. The Scenario's resolves list identifies the Obligation definitions it is designed to satisfy, and the Phase must enable both definitions.

Read the Obligation from top to bottom

The live intent-candidate-required@3 Obligation requires a reviewed Phase 0 foundation to become a frozen candidate.

kind: obligation-definition
id: intent-candidate-required
version: 3
phases: [phase-0-wayfinding]

for_each: '[phase]'
subject_as: required_phase
satisfied_when: 'exists("complete-phase-0-intent-candidates@1", {})'

status_rules:
  - status: blocked
    priority: 200
    when: <foundation evidence is incomplete>
    blocked_by:
      - obligation: product-specification-required@2
        subjects: '[required_phase]'
      # more blockers
  - status: ready
    priority: 100
    when: <foundation evidence is complete>

default_status: blocked
resolve_with:
  scenario: create-phase-0-intent-candidate@1
  inputs:
    definition_members: 'select("phase-0-foundation-members@1", {})'
    member_reviews: 'select("phase-0-foundation-member-reviews@1", {})'
waiver_policy_ref: waiver-applicability@1
  1. kind, id, and version give the definition an exact identity.
  2. phases limits where the definition may apply.
  3. for_each selects Subjects. Here it selects the Active Phase.
  4. subject_as names that Subject for later expressions.
  5. satisfied_when states what evidence satisfies each instance.
  6. status_rules explain whether unsatisfied work is blocked, ready, failed, stale, or awaiting review.
  7. blocked_by identifies earlier Obligation Instances that explain a blocked result.
  8. resolve_with names one Scenario and binds both of its inputs.
  9. waiver_policy_ref delegates waiver rules to a Policy.

Read the Scenario from top to bottom

The live create-phase-0-intent-candidate@1 Scenario receives two groups of exact Revisions.

kind: scenario-definition
id: create-phase-0-intent-candidate
version: 1
phases: [phase-0-wayfinding]

inputs:
  - name: definition_members
    types: [MAP, PSP, STK]
    cardinality: one-or-more
    identity: revision
    conditions: <each member has valid review evidence>
  - name: member_reviews
    types: [REV]
    cardinality: one-or-more
    identity: revision
    conditions: <the exact required Review set is supplied>

outputs:
  - name: candidate
    types: [BSL]
    cardinality: one
    required_links: []

prompt_ref: prompts/create-phase-0-intent-candidate.md@1
review_policy_ref: review-applicability@1
completion: <contract, membership, evidence, and frozen checks>
resolves: [intent-candidate-required]
prohibited_inputs: [<four forbidden input classes>]
batching: single
  1. inputs declares two independent input contracts.
  2. outputs requires one new BSL candidate.
  3. prompt_ref points to the exact agent instructions.
  4. review_policy_ref determines review participation for produced data.
  5. completion validates the proposed transaction as a whole.
  6. resolves declares Resolver semantics for the named Obligation kind.
  7. prohibited_inputs states information the agent must not use.
  8. batching limits how invocations are grouped.

How the two inputs bind

The Obligation and Scenario join by input name:

Scenario input contractObligation binding expression
definition_members
MAP | PSP | STK, one or more exact Revisions		select("phase-0-foundation-members@1", {})
member_reviews
REV, one or more exact Revisions		select("phase-0-foundation-member-reviews@1", {})

The Obligation Instance identifies the exact Subject and Resolver. During Assignment preparation, MDLM reevaluates these binding expressions for that Subject. The resulting Revision identities are stored in the Assignment's invocation bindings.

This corrects one detail from your answer: the exact values are not durable fields stored inside the Obligation Instance.

Can one Scenario resolve several Obligations?

Yes. The live review-datum-in-context@2 Scenario declares that it resolves two Obligation definitions:

  • passing-review-required@2
  • candidate-members-reviewed@2

Each authorizing Obligation binds that Scenario's subject, review_context, and context_members inputs using its own expressions. The Scenario remains one reusable contract.

What the kernel checks

At package load time, generic kernel validation checks:

  • referenced Phase, Scenario, Obligation, Policy, and type identities exist;
  • the Resolver Scenario is enabled wherever its Obligation is enabled;
  • every declared Scenario input has one Obligation binding;
  • bindings use declared input names;
  • binding expression shapes match input identity, cardinality, and type contracts;
  • output links can be produced by their declared Lifecycle Data types.

At Assignment preparation time, the kernel evaluates the bindings against current Lifecycle Data and checks the exact resulting values. Static package validation checks what the expressions can return. Runtime validation checks what they returned this time.

A small design exercise

Suppose a Scenario declares these required inputs:

inputs:
  - {name: subject, types: [PSP], cardinality: one, identity: revision}
  - {name: reviews, types: [REV], cardinality: one-or-more, identity: revision}

An Obligation binds only subject. Predict whether the package loads, and name the missing declaration. Then decide what should happen if reviews is bound correctly but its Selector returns an empty list during evaluation.
