Lesson 1 · 10 to 15 minutes

Who chooses the next work?

Scenarios do not form a sequence. MDLM reevaluates repository facts against package rules after every transaction.

Goal. Explain why a successful Scenario does not tell MDLM what to run afterward.

Eight terms first

Lifecycle Data
Durable Markdown claims and evidence managed by MDLM.
Process Package
Versioned declarations that define types, rules, work contracts, and phase behavior.
Subject
The specific Phase or piece of Lifecycle Data to which a rule applies.
Obligation
A package rule stating what must be true for a Subject.
Obligation Instance
One Obligation applied to one specific subject and package version.
Loose End
An unsatisfied Obligation Instance reported as current work.
Scenario
A reusable contract for bounded agent work. It declares inputs, outputs, and completion checks.
Assignment
One Scenario bound to exact repository facts for one agent response.

What causes work to appear

The agent asks MDLM what to do, performs bounded work, and returns a proposal. The Process Package supplies the rules. MDLM evaluates those rules against Lifecycle Data. If an unsatisfied Obligation is safe to work on, MDLM can return an Assignment for its declared Scenario.

Repository facts
Lifecycle Data and the selected Process Package.
↓ MDLM evaluates
Required outcomes
Obligations say what is missing and whether work can run now.
↓ MDLM returns
One outcome
An Assignment, required attention, a declared stopping point, a dead end, or an invalid result.

The Assignment is temporary orchestration context. It freezes the exact state needed for one proposed transaction. If the proposal passes submission checks, MDLM publishes its outputs as Lifecycle Data. Then the operator reevaluates. The new data may satisfy an Obligation or cause different Obligations to exist.

A small example

Suppose the package requires a Product Specification, a document describing product intent. No valid Product Specification exists.

  1. The applicable Obligation Instance is unsatisfied.
  2. Its Loose End identifies a Resolver Scenario and exact bindings.
  3. If blockers are clear, mdlm next may allocate an Assignment for that Scenario.
  4. The agent proposes the document in its required response packet.
  5. Submission validates the proposal and publishes all transaction outputs together. If validation fails, it publishes none of them.
  6. Reevaluation checks what the new repository state means and derives all current work again.

A successful submission proves that the proposal met the Scenario contract. It does not prove that every lifecycle requirement is now satisfied. MDLM has no hidden "advance to the next step" operation.
