Lesson 3 · 10 to 15 minutes

What exists on disk?

Separate package rules, durable Lifecycle Data, computed results, and the temporary Assignment lease.

Goal. Classify each MDLM concept as stored truth, a computed result, or temporary operator state.

Four kinds of state

Package declaration
A versioned rule shipped in the selected Process Package.
Lifecycle Data
Durable Markdown claims and evidence published through validated transactions.
Derived result
A value MDLM computes from the package and current Lifecycle Data.
Assignment lease
A temporary file reserving one exact unit of work against the current repository state.

Phases contain references, not runtime trackers

The live Phase 0 file lists versioned Obligation and Scenario definitions:

scenarios:
  - establish-initial-wayfinding-map@2
  - compile-psp@3
  - review-datum-in-context@2
  # more Scenario references

obligations:
  - initial-wayfinding-map-required@2
  - product-specification-required@2
  - passing-review-required@2
  # more Obligation references

These are general package declarations. An Obligation Instance is different. MDLM computes an instance by applying one Obligation to one selected Subject under one package reference. It does not write an instance file to track progress.

Stored rule
initial-wayfinding-map-required@2
↓ evaluated for
Exact Subject
phase-0-wayfinding@5 under the selected package
↓ computes
Obligation Instance
Satisfied or unsatisfied, with status, blockers, and a resolver

Run the same evaluation again against unchanged facts and MDLM computes the same instance. Publish new Lifecycle Data and the result may change.

Obligations do not all become Scenario inputs

An Obligation authorizes its Resolver Scenario and binds the Scenario's declared inputs. The Scenario receives those inputs, not the Obligation definition itself.

For the first map, the binding is empty:

resolve_with:
  scenario: establish-initial-wayfinding-map@2
  inputs: {}

Another Obligation might bind a specific Revision as an input. The resulting Assignment records both the authorizing Obligation Instance and the resolved Scenario inputs. Those are different fields with different jobs.

Phase progression has its own rule

A Phase lists applicable Obligations, but that list does not by itself define the transition. The Phase also declares a progression condition, an expression that says when the next Phase is ready, plus any required authority.

progression:
  next_phase: phase-1-product-assurance
  readiness: <expression over exact Lifecycle Data>
  authorization:
    scenario: record-gate-signoff@3
    evidence_selector: applicable-gate-signoffs-for@1

Many Obligations produce evidence used by that expression. Still, "all Obligation Instances are satisfied" and "the progression expression is true" are not interchangeable claims.

The one runtime file

When mdlm next allocates work, it writes .lifecycle/work/active-assignment.json. This is the Assignment lease. It records the package, repository fingerprint, Phase, authorizing Obligation Instance, Scenario, input bindings, and response state.

The initialized repository ignores .lifecycle/work/ in Git. The lease prevents another command from silently allocating incompatible work. It is temporary orchestration state, not Lifecycle Data.

A more exact reevaluation answer

After the map publishes, MDLM reloads the selected package and current Lifecycle Data. It derives the Active Phase, evaluates applicable Obligations into instances, removes satisfied instances from the Loose End list, computes blockers and dispatchability, orders the remaining work, and classifies one Operator Outcome. It creates an Assignment only if that outcome is Assignment or Attention Required.
